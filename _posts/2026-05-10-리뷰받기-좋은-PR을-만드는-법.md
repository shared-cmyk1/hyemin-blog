PR 리뷰를 한 주에 보통 10개쯤 본다. 적은 양은 아니다. 그러다 보니 *리뷰하기 편한 PR*과 *리뷰하기 힘든 PR*의 차이가 너무 명확하게 느껴진다. 오늘은 그 얘기.

## 리뷰어 입장에서 PR을 본다는 것

리뷰어는 PR을 *코드 한 줄씩 읽으면서 이해해 나간다*. 그래서 PR이 다음 조건을 만족할 때 리뷰가 가볍다.

1. **목적이 한 줄로 설명 가능함** (제목 + 요약)
2. **변경이 한 가지 주제로 묶여 있음**
3. **diff가 너무 크지 않음** (감각적으로 500줄 이하)
4. **자동화로 잡힐 건 자동화로 잡힌 상태**

반대로 다음 조건이면 리뷰가 지옥이다.

- 제목이 `fix bug`
- 변경이 5가지 주제로 흩어짐
- diff가 2,000줄
- 린트 / 포맷 / 타입 에러가 함께 묻어 들어옴

후자 PR을 받으면, 진짜로 *리뷰를 미루게 된다*. 사람이라 어쩔 수 없다.

## 좋은 PR의 골격

내가 만드는 PR은 대충 이렇게 생겼다.

```markdown
## 무엇을
사용자 검색 API에서 페이지네이션이 페이지 2 이상에서 깨지던 버그를 고침.

## 왜
정렬 키가 안정적이지 않아서 같은 row가 두 페이지에 걸쳐 나오는 일이 있었음.
재현 이슈: #1234

## 어떻게
- 정렬 키를 (created_at, id) 복합으로 변경
- index도 같이 추가 (migration 002_users_sort.sql)

## 영향 범위
- /api/users 응답 순서가 미세하게 달라짐 (실제로는 거의 동일)
- 다른 API 영향 없음

## 테스트
- 단위 테스트 추가 (`tests/api/users.test.ts`)
- 로컬에서 페이지 1~5 손으로 확인
```

이 정도면 리뷰어가 *읽기 전에 무엇을 봐야 하는지* 안다. 그게 핵심.

## 사이즈에 대해

> 큰 PR은 *전체*가 검토 안 된다. 작은 PR이 *완벽*하게 검토된다.
{: .prompt-warning }

이건 진짜다. 1,500줄짜리 PR을 받으면, 리뷰어는 핵심 파일 2~3개만 정독하고 나머지는 *통과시킨다*. 본인도 그러기 싫지만, 시간이 없어서 그렇게 된다.

작게 쪼개는 게 어렵다. 한 가지 변경을 위해 *주변 정리*까지 필요한 경우가 많기 때문에. 이걸 해결하는 정공법은:

1. **선행 PR**: 리팩토링 / 인터페이스 변경만 따로
2. **본 PR**: 실제 기능 / 버그 픽스
3. **후속 PR**: 다른 호출자들 마이그레이션

이렇게 3개로 쪼개면 각각 200~400줄이고, 리뷰가 깊어진다. 처음엔 귀찮은데 익숙해지면 *오히려 빠르다*. 큰 PR 하나 머지하는 데 일주일 걸리는 거보다, 작은 PR 3개를 각 1~2일에 머지하는 게 결국 빠르다.

## 자기 자신을 먼저 리뷰하기

PR 올리기 전에 반드시 GitHub UI에서 *자기 diff를 다시 읽는다*. 이게 진짜 효과 좋다.

| 자기 리뷰에서 잡히는 것 | 비율(체감) |
| --- | --- |
| 디버깅용 `console.log` / `print` 남은 거 | 30% |
| 주석 처리된 옛날 코드 | 20% |
| 의미 없는 변수명 (a, b, tmp) | 15% |
| 사실은 빼도 되는 import / 변경 | 15% |
| 진짜 버그 | 5% |
| 나머지 | 깔끔함 |

이 30%+20%+15%만 본인이 잡아내도 리뷰어 시간이 절반으로 준다.

```bash
# 내가 자주 쓰는 PR 직전 체크
git diff origin/main --stat       # 변경 파일 수 확인 (너무 많으면 쪼개기)
git diff origin/main | grep -i "console\|TODO\|FIXME"  # 남은 디버그 흔적
```

## 코멘트에 대한 태도

리뷰 받은 코멘트에 *방어적으로* 답하는 사람이 있다. 잘 안다, 나도 옛날에 그랬으니까. 그런데 1~2년 지나서 보면 진짜 후회된다. 리뷰어는 *내 편*이다. 같이 좋은 코드 만들려는 사람이지, 내 자존심을 깎으려는 사람이 아니다.

그래서 지금은 이렇게 답한다.

- "맞아요, 고칠게요" → 한 줄로 끝
- "다른 이유로 이렇게 했어요" → 이유를 한 단락으로 설명
- "더 좋은 방법이 있을 것 같은데 같이 고민해 주세요" → 솔직하게 SOS

방어를 줄이면 리뷰 사이클이 짧아진다. 그게 결국 본인한테 좋다.

## 마무리

리뷰는 두 사람이 하는 게임이다. 제출자가 *읽기 좋게* 만들수록 리뷰어가 *깊게* 봐주고, 리뷰어가 *친절하게* 답할수록 제출자가 *덜 방어적으로* 답한다. 이 두 방향이 같이 움직여야 팀이 좋아진다.

오늘도 누가 또 1,500줄짜리 PR을 올렸는데... 일단 커피 한 잔 더 내리고 시작해야겠다.
